## Detailed Findings

### W02-001 - Python Settings validation allows a config the PowerShell runtime rejects

- Severity: High
- File / symbol: `src/mediapipeline/core/config/validation.py:234` `validate_config_values`; `src/mediapipeline/core/config/validation.py:271` delegates root path checks to warnings. PowerShell runtime enforcement is in `ops/pipeline/engine/config/schema_validation.ps1:151` `Test-MediaPipelineConfigPathShape`, with nested root errors emitted at `ops/pipeline/engine/config/schema_validation.ps1:187`.
- Problem: The Python validation path used by Settings preview/save treats root path overlap as warnings via `config_root_path_warnings`, but the PowerShell runtime schema treats the same `SourceMovies`/`Outsource`, `SourceTV`/`Outsource`, or `LocalBase` nesting as hard errors.
- Impact: An operator can save settings that look warning-only in the backend Settings path, then the actual pipeline launch fails schema validation. This undermines Settings as the authoritative preflight for source/output/scratch separation.
- Evidence:
  - In-memory Python validation with `SourceMovies = C:\Media` and `Outsource = C:\Media\Processed` returned `errors []` and warning `Outsource is inside SourceMovies. Keep source, output, and scratch roots separated.`
  - PowerShell schema validation with equivalent default config overrides returned `Ok=False` and `Errors=Outsource and SourceMovies must not be nested inside each other.`
- Fix direction: Make Python save validation match runtime launch validation for root path overlap. Either promote these root overlap warnings to errors in `validate_config_values` for save/patch paths, or have `validate_config_document_for_save_for_service` run `Test-MediaPipelineConfigSchema` instead of syntax-only `Import-PowerShellDataFile`.
- Suggested validation: Add tests that Settings Preview/Save rejects equal/nested `SourceMovies`, `SourceTV`, `Outsource`, and `LocalBase` combinations, and add a Python/PowerShell schema parity test for root path overlap cases.

### W02-002 - Companion sidecar discovery can include adjacent media files

- Severity: High
- File / symbol: `src/mediapipeline/core/final_library/promotion_parts/transfer.py:373` `companion_sidecars`; prefix inclusion at `src/mediapipeline/core/final_library/promotion_parts/transfer.py:386`; cleanup caller at `src/mediapipeline/core/final_library/promotion.py:592`.
- Problem: `companion_sidecars(primary)` first checks that the primary is a media file, then includes every sibling file whose name starts with `primary.stem + "."`. It does not exclude media suffixes for the companion files.
- Impact: A publish folder containing `Movie.mkv` and an adjacent media file like `Movie.sample.mkv`, `Movie.trailer.mp4`, or another dot-suffixed media variant can have that adjacent media copied to the final library destination as if it were a sidecar. When `FinalLibraryPromotionCleanupAfterVerified` is enabled, `cleanup_verified_files` receives the copied file evidence and deletes the adjacent publish-root media file after verification.
- Evidence: The inclusion predicate is only `item.is_file()`, `item != primary`, `item.name.startswith(prefix)`, and not containing `.promotion-`; it does not check `item.suffix` against `MEDIA_FILE_SUFFIXES` even though `MEDIA_FILE_SUFFIXES` is imported at `transfer.py:10`.
- Fix direction: Restrict companions to explicit sidecar suffixes/manifest extensions, or exclude `item.suffix.casefold() in MEDIA_FILE_SUFFIXES` from companion collection unless a deliberate media-companion policy exists.
- Suggested validation: Add a final-library promotion unit test where `Movie.mkv`, `Movie.en.srt`, and `Movie.sample.mkv` share a folder. The expected copy plan should include the `.srt` sidecar and exclude the second media file, including when cleanup-after-verified is enabled.
