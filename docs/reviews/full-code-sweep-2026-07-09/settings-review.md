# Settings-tab full code sweep — 2026-07-09

## Executive assessment

The normal Settings Patch workflow has a sound backend-owned shape: the WebView stages a patch, the backend validates and redacts its preview, and a save requires literal `confirm_save: true` plus a review-confirmation digest recomputed from the current candidate. JSON authority is projected to PSD1 only after serialization and PowerShell round-trip validation, with rollback on write failure.

However, the audit found three P1 boundary failures and one P2 review-binding gap. In particular, the documented secret exclusion is not enforced for raw patch submissions, imported unknown “legacy extras” are not inert in the PowerShell runtime, and concurrent saves can lose a preceding save because the lock is process-local and is released before reload refreshes the cached base configuration.

## Findings

### P1 — CSW-2026-07-09-SETTINGS-001: hidden network tokens can still be submitted through WebView raw patching

**Evidence.** The canonical raw-key guidance says `CoordinatorAuthToken` and `WorkerAuthToken` are not offered for WebView raw JSON and must be edited directly in PSD1 because they must not reach browser storage, DevTools, or JS heap ([`SETTINGS_RAW_KEY_TRIAGE.md:72`](../../docs/architecture/SETTINGS_RAW_KEY_TRIAGE.md#L72)-[`77`](../../docs/architecture/SETTINGS_RAW_KEY_TRIAGE.md#L77)). In practice, normal save parses the unrestricted `settings-patch-json` object and sends it to Preview/Save ([`settingsView.js:2456`](../../apps/desktop/webview/static/assets/settingsView.js#L2456)-[`2527`](../../apps/desktop/webview/static/assets/settingsView.js#L2527)). Candidate validation accepts any registered sensitive key unless its value is exactly `"<redacted>"` ([`settings_patch_candidate_facade.py:304`](../../src/mediapipeline/core/config/settings_patch_candidate_facade.py#L304)-[`318`](../../src/mediapipeline/core/config/settings_patch_candidate_facade.py#L318)). The test suite intentionally confirms that a preview accepts a replacement `CoordinatorAuthToken` ([`test_application_facade_settings_patch.py:118`](../../tests/python/desktop/test_application_facade_settings_patch.py#L118)-[`166`](../../tests/python/desktop/test_application_facade_settings_patch.py#L166)).

**Impact.** A caller can put a real token in the raw textarea, request body, in-memory save evidence, and browser tooling, violating the stated secret boundary even though server response diffs/review entries redact it. This is a confidentiality boundary failure, not merely a display issue.

**Recommended handoff.** Settings/API security owner: reject sensitive config keys on `preview-patch` and `save-patch` (except a purpose-built secret channel), add a frontend raw-key preflight block, and add HTTP/static regression coverage proving real token values never enter WebView settings requests or client state.

### P1 — CSW-2026-07-09-SETTINGS-002: legacy extras are projected and dynamically applied, so they are not inert

**Evidence.** Migration separates unknown keys into `legacy_extras` ([`settings_store.py:132`](../../src/mediapipeline/core/config/settings_store.py#L132)-[`205`](../../src/mediapipeline/core/config/settings_store.py#L205)), but projection merges those extras back into the PSD1 values ([`settings_store.py:229`](../../src/mediapipeline/core/config/settings_store.py#L229)-[`234`](../../src/mediapipeline/core/config/settings_store.py#L234)). PowerShell schema validation checks required/path/policy rules but does not reject unregistered keys ([`config_schema.ps1:15`](../../ops/pipeline/engine/config/config_schema.ps1#L15)-[`45`](../../ops/pipeline/engine/config/config_schema.ps1#L45)). Finally, runtime merge executes `Set-Variable -Scope Script` for every imported key that is not on its reserved-name list ([`runtime_merge.ps1:20`](../../ops/pipeline/engine/config/runtime_merge.ps1#L20)-[`43`](../../ops/pipeline/engine/config/runtime_merge.ps1#L43)). The import test itself calls the extra `LegacyLabOnlyToggle` “keep-for-projection” ([`test_settings_store.py:118`](../../tests/python/desktop/test_settings_store.py#L118)-[`149`](../../tests/python/desktop/test_settings_store.py#L149)), while the route inventory calls legacy extras “inert” ([`API_ROUTE_INVENTORY.md:257`](../../docs/inventories/API_ROUTE_INVENTORY.md#L257)-[`258`](../../docs/inventories/API_ROUTE_INVENTORY.md#L258)).

**Impact.** An unregistered PSD1 key can create or overwrite a non-reserved script-scoped variable. Whether it currently influences a particular module is accidental and can change as modules evolve; the legacy-extra safety claim is therefore false. This also turns import of arbitrary prior PSD1 data into a wider runtime namespace surface.

**Recommended handoff.** PowerShell/config owner: keep extras only in the JSON envelope and projection manifest, do not emit them to active PSD1; alternatively, make `Set-MediaPipelineRuntimeConfigVariables` accept only `Get-MediaPipelineKnownConfigKeys` and explicitly reject unknown PSD1 keys at schema validation. Add an execution-level test that an unknown imported key cannot appear as a script variable.

### P1 — CSW-2026-07-09-SETTINGS-003: save locking lacks version/CAS protection and permits a stale concurrent overwrite

**Evidence.** The application creates only an in-process `threading.Lock` ([`facade.py:126`](../../src/mediapipeline/desktop/application/facade.py#L126)-[`139`](../../src/mediapipeline/desktop/application/facade.py#L139)); save acquires it non-blockingly and releases it in `finally` immediately after persistence ([`settings_patch_facade.py:187`](../../src/mediapipeline/core/orchestration/settings_patch_facade.py#L187)-[`225`](../../src/mediapipeline/core/orchestration/settings_patch_facade.py#L225)). Local-API reload happens only after `save_settings_patch` returns, outside that lock ([`commands_settings.py:252`](../../src/mediapipeline/core/api/commands_settings.py#L252)-[`263`](../../src/mediapipeline/core/api/commands_settings.py#L263)). Candidate construction uses `resolved.config_data` as its base ([`settings_patch_candidate_facade.py:264`](../../src/mediapipeline/core/config/settings_patch_candidate_facade.py#L264)-[`266`](../../src/mediapipeline/core/config/settings_patch_candidate_facade.py#L266)), and review confirmation authenticates that cached base digest, not a store/PSD1 generation checked at commit ([`settings_patch_policy.py:91`](../../src/mediapipeline/core/config/settings_patch_policy.py#L91)-[`123`](../../src/mediapipeline/core/config/settings_patch_policy.py#L123)).

**Impact.** Two requests that pass preview against the same loaded base can serialize through the lock but still each write a full merged candidate. The second can acquire the lock after the first releases it but before reload refreshes `resolved.config_data`, then overwrite the first request’s unrelated changes. A second local API process or direct store/PSD1 writer is also outside the lock. The current review match proves request integrity, not current-authority freshness.

**Recommended handoff.** Settings persistence owner: add an authority generation/digest to workspace, preview, and save; compare-and-swap it while holding a cross-process file/store lock; reload/update the resolved base before lock release. Add a deterministic two-client test for disjoint concurrent patches and an external-generation-change test.

### P2 — CSW-2026-07-09-SETTINGS-004: Settings Wizard does not bind its displayed preview to the subsequent save

**Evidence.** The WebView requires a locally fresh wizard preview before enabling save ([`settingsWizard.js:346`](../../apps/desktop/webview/static/assets/settingsWizard.js#L346)-[`359`](../../apps/desktop/webview/static/assets/settingsWizard.js#L359)), but sends only `{ wizard, confirm_save: true }` ([`settingsWizard.js:1032`](../../apps/desktop/webview/static/assets/settingsWizard.js#L1032)-[`1054`](../../apps/desktop/webview/static/assets/settingsWizard.js#L1054)). The wizard save route likewise accepts only `confirm_save` ([`settings_wizard.py:209`](../../src/mediapipeline/core/config/settings_wizard.py#L209)-[`221`](../../src/mediapipeline/core/config/settings_wizard.py#L221)); for existing configs it silently creates a fresh backend preview and injects that fresh review confirmation itself before calling normal patch save ([`settings_wizard.py:252`](../../src/mediapipeline/core/config/settings_wizard.py#L252)-[`266`](../../src/mediapipeline/core/config/settings_wizard.py#L266)). First-run save bypasses the normal review-confirmation function entirely ([`settings_wizard.py:786`](../../src/mediapipeline/core/config/settings_wizard.py#L786)-[`878`](../../src/mediapipeline/core/config/settings_wizard.py#L878)).

**Impact.** The save remains validated and confirmation-gated, but the confirmation is not evidence that the operator reviewed the exact backend candidate written. A changed base, normalization, or policy warning between the displayed preview and save can be saved without being shown in the prior review. This is weaker than the normal Settings Patch contract advertised in the route inventory ([`API_ROUTE_INVENTORY.md:256`](../../docs/inventories/API_ROUTE_INVENTORY.md#L256)-[`264`](../../docs/inventories/API_ROUTE_INVENTORY.md#L264)).

**Recommended handoff.** Settings Wizard owner: return the normal review confirmation from wizard preview and require it on wizard save, including first-run candidate review; invalidate it on wizard/config-generation changes. Keep the existing danger acknowledgements, but do not use them as a substitute for candidate binding.

## No-finding coverage

- **Normal strict confirmation and review matching:** confirmed for `/api/settings/save-patch`; absent or non-boolean `confirm_save` is rejected, and every review digest component plus exact changed/removed lists is compared.
- **Backend mutation ownership:** structured builders stage JSON only. The inspected nine `settingsView.builders.*.js` modules contain no HTTP calls, filesystem calls, FFmpeg invocation, publish/drain action, or browser persistence of settings; their apply functions feed the common Save path. Path browsing is backend allowlisted and stages only ([`commands_settings.py:142`](../../src/mediapipeline/core/api/commands_settings.py#L142)-[`238`](../../src/mediapipeline/core/api/commands_settings.py#L238)).
- **Safe projection mechanics:** serializer validation, temporary PSD1 re-import comparison, byte-backup rollback, and last-good snapshot generation are present. The audit found no bypass from the frontend to JSON store or generated PSD1 projection.
- **Alias and spelling policy:** aliases are small and import-only; normal patch rejects aliases/case variants through canonical-spelling checks. Import rejects canonical case duplicates.
- **Backend response redaction:** workspace, preview diff, and review entries recursively redact keys containing token/password/secret/credential/API-key markers ([`settings_helpers_facade.py:72`](../../src/mediapipeline/core/config/settings_helpers_facade.py#L72)-[`123`](../../src/mediapipeline/core/config/settings_helpers_facade.py#L123)). This does not mitigate finding -001 because request-side exposure remains possible.
- **Frontend stale response/failure handling:** preview ignores superseded request IDs and textarea changes; save does not proceed if its preview becomes stale. Save timeout and post-save refresh failure state are explicit rather than treated as success.
- **Python/PowerShell key parity design:** Python tests compare Python registry, Pydantic fields, JSON schema, PowerShell registry/order, and WebView consumers ([`test_config_keys.py:106`](../../tests/python/desktop/test_config_keys.py#L106)-[`165`](../../tests/python/desktop/test_config_keys.py#L165)). PowerShell checks registry/schema/defaults/enums and scans engine literal config references for unknown keys ([`Invoke-ConfigKeyRegistryChecks.ps1:280`](../../ops/pipeline/tests/Unit/Invoke-ConfigKeyRegistryChecks.ps1#L280)-[`308`](../../ops/pipeline/tests/Unit/Invoke-ConfigKeyRegistryChecks.ps1#L308); [`500`](../../ops/pipeline/tests/Unit/Invoke-ConfigKeyRegistryChecks.ps1#L500)-[`525`](../../ops/pipeline/tests/Unit/Invoke-ConfigKeyRegistryChecks.ps1#L525)).

## Test and contract assessment

The static test inventory is strong for the happy-path patch contract: strict confirmation, tampered review confirmation, secret redaction/placeholder rejection, save lock busy behavior, unknown-key rejection, JSON-store drift/recovery/rollback, alias migration, wizard path/danger checks, and cross-language key parity are all represented. The route inventory correctly identifies `save-patch` as high-risk and documents its review contract.

Missing regression coverage maps directly to the findings:

- No test rejects a real sensitive key/value submitted through the WebView raw patch route; the existing unit test proves it is accepted.
- No test executes PowerShell runtime initialization against an imported legacy extra and proves it cannot create script scope.
- No two-client/version-generation test proves disjoint settings patches cannot overwrite one another.
- No wizard test requires a client-supplied review confirmation matching the preview the operator saw; the existing tests accept server-side automatic confirmation construction.

No test commands were executed for this audit: the requested scope is read-only and the existing repository worktree is substantially dirty, including settings/config-related files. Assessment is from source, contract, inventory, and test inspection only.

## Coordinator handoff

1. **Security/settings API:** resolve -001 before treating Settings as a safe secret boundary; decide on a dedicated native/OS credential channel or prohibit token mutation through WebView entirely.
2. **Config/PowerShell:** resolve -002 before accepting the route-inventory claim that legacy extras are inert; preserve them as non-executed archive metadata or tighten the runtime allowlist.
3. **Persistence/concurrency:** resolve -003 with a cross-process authority generation/CAS protocol; this should precede any broader multi-window or multi-operator Settings work.
4. **Wizard:** resolve -004 by reusing normal preview-confirmation binding end-to-end, including first-run candidate review.

## Limits

- This is a code and contract audit, not a live save/import/reload or PowerShell execution test. No settings mutation route, file save, config import, or media command was invoked.
- The source tree had extensive unrelated uncommitted changes at audit start, including `src/mediapipeline/contracts/config.py`, settings metadata/validation-adjacent Python and PowerShell files, tests, inventories, and generated summaries. Findings cite the observed working tree, not a clean commit baseline.
- The audit reviewed the requested Settings partial, main view, nine builder modules, settings helper modules, wizard, metadata/raw-triage/safety/review paths, API settings payloads, store/migration/alias/projection code, PowerShell registries/runtime, inventories, and targeted tests. It did not independently prove runtime behavior on a representative media file; real-media validation is not applicable to this read-only configuration-surface audit.
