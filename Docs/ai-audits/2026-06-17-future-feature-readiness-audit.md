## Recommended 6-Month Architecture Investment Plan

1. Months 1-2: harden read-only distributed observability by adding backend-owned coordinator queue reporting, worker capability read models, and scheduler explanation contracts without adding mutation controls [E5][E7][E11][E14].
2. Months 1-2: start the durable-state path by identifying which queue, worker, lifecycle, preset, command, and audit records must move beyond JSON/session-memory authority before remote or multi-operator features [E6][E13][E15].
3. Months 2-3: extract capability facts into a reusable worker capability inventory and add deterministic scheduler dry-runs that explain assignment decisions before changing actual claim behavior [E7][E8][E11].
4. Months 3-4: promote richer preset management into backend-owned PresetV2 CRUD/import/export/validate/preview while preserving legacy patch compatibility and requiring real-media validation for policy-changing presets [E2][E9][E11].
5. Months 4-5: add a backend event journal/notification adapter and one low-risk notification provider behind redacted settings, test-send routes, retries, and delivery history [E3][E5][E7][E12].
6. Months 5-6: pilot read-only mobile/remote status against the strengthened read contracts, but keep remote mutation controls disabled until durable remote auth/RBAC and command attribution exist [E3][E5][E13][E14].

## Features That Should Wait

Cloud sync should wait until durable state, repair/reconcile dry-runs, credential handling, and pending-publish-safe sync manifests exist [E1][E3][E13][E15].

Multi-operator access should wait until durable identity, RBAC, command attribution, locks, and conflict handling exist [E1][E3][E13].

General plugin architecture should wait until there is a narrow backend-only extension model, permissions, sandboxing, and audit infrastructure; current contracts explicitly exclude plugin execution [E3][E12].

Production AI upscaling should wait until capability scheduling, model/tool allowlisting, preset policy extensions, and real-media validation fixtures exist [E2][E10][E11].

Remote mutation-oriented management should wait until local auth is separated from remote auth and route permissions are explicit in the contract [E3][E5].

## Features That Are Nearly Ready

Richer preset management is the closest candidate because the schema, display adapters, validation, legacy migration, and backend Preview/Save boundary already exist [E9][E11].

Read-only distributed worker observability is close because lifecycle contracts, worker state, protocol objects, and WebView read-only guardrails already exist; the missing piece is a backend-owned coordinator queue reporting contract [E5][E7][E14].

Initial hardware capability visibility is close because telemetry and encoding capability validation already exist; actual scheduling is not yet close because coordinator queue selection is not capability-scored [E7][E11].

Read-only mobile dashboard status is plausible after aggregation and remote-auth decisions because the Local API already exposes queue, metrics, settings evidence, worker state, and close-readiness [E3][E5].

## Highest-Risk Blockers

The largest blocker is durable shared state: JSON remains authoritative, lifecycle state includes session-memory scope, and future remote/multi-operator/cloud features need durable, conflict-aware records [E6][E13].

The second blocker is security scope: the current API is intentionally local and per-run-token based, so remote management, mobile control, multi-operator access, cloud sync, and plugins require a different auth/RBAC/secret model [E3][E4].

The third blocker is mutation ownership: WebView and remote surfaces must not bypass backend-owned media, queue, settings, publish, rename, lifecycle, or state mutation routes [E1][E14].

The fourth blocker is missing capability scheduling: workers can report/access libraries and map encoders, but there is no normalized capability scheduler for GPU, VRAM, model/tool availability, dynamic load, or scratch budget [E7][E8][E11].

The fifth blocker is absent provider abstraction: no active cloud sync, notification provider, AI upscaler provider, or plugin execution framework exists in active source [E10][E12].

## Safest Sequencing

1. Add read-only evidence first: coordinator queue reporting, worker capability inventory, scheduler explainability, and preset library reads [E5][E7][E9][E11][E14].
2. Add dry-runs second: scheduler dry-runs, queue mutation dry-runs, notification test-send dry-runs, preset apply preview, and cloud/repair reconcile dry-runs [E5][E9][E11][E15].
3. Add durable state third: move the minimum required queue, worker, lifecycle, preset, event, and audit records into a durable authority before off-host or multi-operator mutation controls [E6][E13].
4. Add confirmed mutation routes fourth: only after dry-runs and durable state exist, add command-journaled confirmed routes for queue actions, preset apply, notification delivery, and lifecycle changes [E3][E5][E6][E14].
5. Add remote/mobile access fifth: keep it read-only until remote auth/RBAC/session semantics are implemented and validated [E3][E5].
6. Add media-transforming future features last: AI upscaling and advanced hardware scheduling should follow capability inventory, scheduler validation, tool allowlisting, and representative real-media validation [E2][E10][E11].

## Limitations

This audit did not run real-media validation, Local API/Tauri smokes, or security tests because the requested task was report-only and no runtime behavior was intentionally changed [E0][E2].

This audit used targeted source/document reads and searches rather than a full-file read of the entire repository; the startup docs and generated summaries were used to keep the review within the repository's token-conservation rules [E0].

Several feature-absence conclusions rely on active-source searches and route-contract evidence, so newly untracked or future files outside the searched active paths could change those conclusions after they are incorporated into the canonical source tree [E0][E12].
