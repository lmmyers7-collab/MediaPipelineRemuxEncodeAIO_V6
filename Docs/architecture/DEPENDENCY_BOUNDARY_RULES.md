# Dependency Boundary Rules

Created: 2026-05-31

This document records the Phase 0 dependency-cleanup baseline and the local
checker that reports it. It is architecture/tooling guidance only. It does not
change runtime behavior, media policy, queue behavior, publish/drain behavior,
settings persistence, source/scratch/output movement, or WebView/Tauri
ownership.

## Command

Run from the V6 repository root with the bundled Python interpreter:

```powershell
.\DesktopApp\Runtime\Python\python.exe .\scripts\dev\check_dependency_boundaries.py
```

The checker is stdlib-only and offline-safe. As of Phase 5, the default mode
enforces hard dependency rules and exits nonzero for unallowlisted hard
findings. Use `--report-only` only when collecting diagnostic output without
blocking on findings:

```powershell
.\DesktopApp\Runtime\Python\python.exe .\scripts\dev\check_dependency_boundaries.py --report-only
```

Useful options:

- `--format json` emits the dependency report and enforcement report as
  structured JSON.
- `--max-internal-imports N` limits the printed internal import rows; `0`
  prints every internal `app.*` import edge.
- `--allowlist <path>` uses an alternate hard-rule allowlist. The default is
  `Docs/architecture/dependency_boundary_allowlist.txt`.

## Edge Convention

The dependency-boundary checker uses this convention:

```text
A -> B means A imports B.
```

This differs from `Docs/generated/DEPENDENCY_GRAPH.md`, whose generated domain
graph follows dependency-domain to consuming-domain convention. For example, in
that generated graph `config --> api` means API code imports config code.

The dependency atlas CSV files generated by
`scripts/dev/generate_dependency_atlas.py` use importer to imported-module
columns (`source_module,target_module`). Phase work must verify the convention
of the artifact being inspected before drawing conclusions.

## Reported Signals

`scripts/dev/check_dependency_boundaries.py` scans Python modules under `app/`
with `ast` and reports:

- internal imports among `app.*` modules;
- module-level cycles;
- package-level cycles, where package means the first two module segments such
  as `app.config`;
- direct imports from `app.shared`;
- direct imports from `app.shared.utils`;
- direct imports from `app.shared.constants`;
- direct imports from `app.shared.protocols`;
- forbidden imports from `app.config` to higher-level runtime, UI, or workflow
  packages;
- forbidden imports from `app.api` to `app.ui`;
- forbidden status/observability/telemetry direction violations.

## Boundary Rules

Phase 5 enforces hard rules by default. Warning-only rules remain visible while
their owning cleanup phases continue.

Hard failure rules:

- `NO_PACKAGE_CYCLES`: package-level cycles are not allowed.
- `NO_MODULE_CYCLES`: module-level cycles are not allowed unless specifically
  allowlisted.
- `NO_CONFIG_TO_ORCHESTRATION`, `NO_CONFIG_TO_DECIDE`, and
  `NO_CONFIG_TO_HIGHER_LEVEL`: `app.config` must not import higher-level
  packages such as `app.api`,
  `app.decide`, `app.observability`, `app.orchestration`, `app.processes`,
  `app.publish`, `app.queue`, `app.rename`, `app.status`, `app.telemetry`, or
  `app.ui`.
- `NO_API_TO_UI`: `app.api` must not import `app.ui`.
- `NO_DIRECT_APP_SHARED_IMPORTS`: direct `app.shared` imports are not allowed.
- The chosen status direction is:

  ```text
  app.status -> app.observability -> app.telemetry
  ```

  Under the checker convention, `NO_OBSERVABILITY_TO_STATUS`,
  `NO_TELEMETRY_TO_OBSERVABILITY`, and `NO_TELEMETRY_TO_STATUS` fail for
  opposite-direction imports.
- `PYTHON_PARSE_ERRORS`: app-source parse errors fail because the static import
  graph cannot be trusted.

Warning rules:

- `NO_SHARED_UTILS_IMPORTS`
- `NO_SHARED_CONSTANTS_IMPORTS`
- `NO_SHARED_PROTOCOLS_IMPORTS`
- `NO_BARREL_INIT_REEXPORTS`
- `NO_DOMAIN_IMPORTS_FROM_SHARED_CONSTANTS`

Direct `app.shared` imports are reported separately from direct
`app.shared.utils`, `app.shared.constants`, and `app.shared.protocols` imports
so later phases can reduce the shared blast radius without hiding the current
baseline.

## Allowlist Workflow

Hard-rule allowlist entries live in
`Docs/architecture/dependency_boundary_allowlist.txt`. Each non-comment line is
pipe-delimited:

```text
importing module | imported module | rule id | reason | target removal phase or owner
```

Use the narrowest possible module or package edge. Do not add warning-only
rules to the allowlist. The checker validates that allowlist rows are
well-formed, use known hard-rule IDs, and still correspond to a current hard
finding. Malformed rows, unknown rule IDs, and stale rows fail the command.

Temporary allowlist entries are acceptable only when fixing the edge is outside
the current phase's safe scope. Each entry must explain why it remains and who
owns removal.

As of the final 2026-05-31 dependency cleanup pass, the allowlist has no active
entries.
