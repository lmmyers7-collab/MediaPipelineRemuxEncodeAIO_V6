# File summaries

This file points at `summaries/` and explains how it works. It is the
short version of the per-file map; for the long list, see
`PROJECT_INDEX.md` in this folder.

## What's in `summaries/`

One Markdown summary per source file, generated by
`scripts/dev/refresh_summaries.py` from `app/`, `engine/`, `scripts/`,
`tests/`, `DesktopApp/mediapipeline_desktop_app/`, and
`Pipeline/Modules/`. Today there are 410 summaries for
~30 MB of source — about a 15× compression ratio for AI sessions.

Each summary mirrors the source path:

```
app/publish/drain.py                  →  summaries/app/publish/drain.py.md
Pipeline/Modules/Audit.Audio.ps1      →  summaries/Pipeline/Modules/Audit.Audio.ps1.md
```

## Summary format

YAML frontmatter plus a short body:

```markdown
---
file: app/publish/drain.py
pipeline_stage: publish
token_priority: high | medium | low
last_reviewed: YYYY-MM-DD
last_modified: YYYY-MM-DD
sha256: <hex>
owner_domain: publish
related: [app/publish/pending.py, app/storage/db.py, engine/publish/]
---
# <path>

**Purpose:** one sentence.

**Key responsibilities:** 3-7 bullets.

**Inputs / Outputs:** types or short descriptions.

**Important symbols:** list with one-line descriptions.

**Dependencies (in-repo):** module list.

**Side effects:** filesystem, DB, locks, subprocesses.

**Config used:** dotted config keys.

**Pipeline stage:** stage name + schema reference.

**Known risks:** edge cases worth knowing before editing.

**Token priority:** one of high / medium / low + one-line reason.
```

## Token-priority taxonomy

- **High**: pipeline-critical, behavior-defining. Read full source
  when editing related area.
- **Medium**: adapters, DTOs, route handlers. Summary suffices unless
  editing this file.
- **Low**: generated, vendored, pure glue.

## SHA-256 drift rule

The `sha256` field in each summary frontmatter is the SHA-256 of the
source file at the time the summary was written. If the source file
changes without the summary being regenerated, the hash no longer
matches. The pre-commit hook (Phase 4 — planned) and CI both fail on
mismatch.

Regenerate after edits:

```powershell
python scripts/dev/refresh_summaries.py
```

The script walks tracked source files, detects which summaries are
stale by hash, and rewrites only those.

## Rules for AI sessions

1. Start by reading `AGENTS.md`, `Docs/generated/PROJECT_INDEX.md`,
   `Docs/architecture/ARCHITECTURE.md`, and
   `Docs/generated/PIPELINE_MAP.md`. Archived session notes live under
   `Docs/archive/sessions/` and are historical only.
2. For each file you intend to edit, read its summary in `summaries/`.
3. Only open the full source if the summary marks it `high` or the
   change requires a function the summary did not list.
4. After editing, run `python scripts/dev/refresh_summaries.py` (or let
   the pre-commit hook do it).
5. Do not duplicate long code blocks into summaries — they name
   symbols and intent, source files contain code.
6. Track file ownership via `owner_domain` in frontmatter.
7. Maintain a context budget of roughly 80 KB summaries plus 50 KB
   full sources per task.

## When to regenerate

- After editing any source file (pre-commit will catch it).
- When `app/contracts/` changes (so `pipeline_stage` mappings stay
  current).
- When adding a new file (the script picks it up on the next walk).

## What `summaries/` is *not*

- Not a substitute for ADRs (architectural decisions).
- Not a substitute for `Docs/generated/PIPELINE_MAP.md` (wire contracts).
- Not a substitute for the source file (no code blocks).
- Not edited by hand — regenerate instead.
